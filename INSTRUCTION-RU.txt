AUREVON — ИНСТРУКЦИЯ ПО ВОССТАНОВЛЕНИЮ И ПЕРЕНОСУ

1. КАКОЙ АРХИВ ИСПОЛЬЗОВАТЬ
AUREVON-local-complete — частная копия локального проекта, истории файлов, доступных локальных баз и материалов. Не загружать в GitHub: внутри могут находиться закрытые настройки и данные.
AUREVON-deploy-package — очищенная текущая локальная сборка для переноса кода. Распаковать перед загрузкой в репозиторий. Сам ZIP не является форматом запуска Railway.

2. ЧТО НЕ СОХРАНЕНО С РАБОЧЕГО СЕРВЕРА
Актуальные базы Railway /data/inquiries.sqlite (магазин) и /data/aurevon-bot.sqlite (бот), секретные Variables и настройки BotFather не экспортированы. Локальные базы в резервной копии не заменяют эти рабочие базы.
Точное совпадение локальной сборки с текущей веткой main GitHub не подтверждено. Перед публикацией сравнить с private-репозиторием tdom7274/AUREVON-STORE: в нем могут быть более свежие изменения Dockerfile и других файлов.

3. ВОССТАНОВЛЕНИЕ ЛОКАЛЬНОЙ КОПИИ
Распаковать частный архив в НОВУЮ папку. В workspace/outputs/AUREVON-railway находится текущая локальная облачная сборка; остальные outputs могут содержать предыдущие версии.
Проверить контрольную сумму ZIP по соседнему файлу .sha256. Список файлов и их SHA256 находится в BACKUP-MANIFEST.json.
Доступные локальные SQLite-базы сохранены согласованными снимками и проверены integrity_check. Не заменять ими рабочие базы без осознанного решения.

4. GITHUB → RAILWAY
Распаковать deploy-package в отдельную папку. Корень репозитория должен содержать package.json, Dockerfile, cloud.mjs, app/ и bot/.
Сравнить с текущим main, сохранить актуальные изменения, не публиковать .env, токены, базы и частный backup. Перед подключением автодеплоя подготовить отдельную проверочную ветку/среду.
В каталоге сборки выполнить npm test на Node >=24.13.0 и <25. Эти проверки требуется повторить перед переносом; создание архива само по себе не проверяет работоспособность сервиса.
Магазин: Railway service AUREVON-STORE, railway.json и Dockerfile.
Бот: отдельный service AUREVON-BOT, railway.bot.json и Dockerfile.bot. Не запускать второго обработчика того же Telegram-бота параллельно.
Секреты и рабочие адреса задать через закрытые Variables по документации сборки и текущим настройкам. Использовать отдельный постоянный Volume /data для каждого сервиса.
Если переносится действующий магазин, сначала получить согласованные снимки ОБЕИХ рабочих баз и защищенную копию Variables. Восстанавливать базы при остановленном соответствующем процессе; простое копирование работающей SQLite без учета WAL ненадежно.

5. ДРУГОЙ ХОСТИНГ
Нужен хостинг с совместимым Node/Docker, постоянным хранилищем, HTTPS и возможностью запуска процесса бота. Статический либо PHP-only хостинг не запускает эту Node-сборку без адаптации.
Изображения из app включены. Внешние видео и другие URL сохраняют зависимость от внешних поставщиков.

6. TELEGRAM И ПРОВЕРКА ПОСЛЕ ПЕРЕНОСА
Текущий адрес магазина: https://aurevon-store-production.up.railway.app/
Mini App: https://t.me/Aurevon_outlet_bot/luxury_watches
При смене адреса обновить URL приложения/меню в BotFather и связанные настройки. Сам архив настройки Telegram не переносит.
Проверить главную, каталог, поиск, фильтры, фото, карточку, избранное, корзину, запуск из Telegram, /start и передачу обращения менеджеру. Проверить сохранение базы после перезапуска, HTTPS и отсутствие секретов в публичных файлах. Проверочную заявку явно пометить тестовой.
Рабочий сервис переключать только после проверки, сохранив предыдущую версию и рабочие базы для отката.

Статус: проверенная локальная резервная копия; полный снимок работающей инфраструктуры Railway пока НЕ получен.
